# 糖豆人会员系统 交付说明

这份文档说明会员系统在哪些文件里实现、奖励制度是什么口径、验证到什么程度、还有什么没做。

> 本次是**奖励制度改版**：由原来的「十次一周期（第 2/5/8/10 次给 £2 / £5 / 本人 85 折 + 朋友 9 折 / VIP 月卡）」改成
> 「**到店折扣阶梯（第 3/5/7/10 次给 9 折 / 8 折 / 7 折 / 5 折）**」。VIP 月卡、£2 / £5 券、朋友折扣全部移除。

---

## 一、怎么跑起来

**1. 环境变量**（不进仓库，自己建 `.env.local`）

```
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_ANON_KEY=
SUPABASE_SERVICE_ROLE_KEY=
NEXT_PUBLIC_APP_URL=
```

**2. 执行迁移**（必须，否则会员功能不可用）

把 `supabase/migrations/016_members.sql`、`017_member_settlement.sql` 按顺序发到数据库执行一次。
怕顺序搞错就直接用 **`docs/上线迁移-一次执行.sql`**（两个文件已按顺序合并成一份，粘一次、按一次 Run 即可）。

测试库 `rlakqwmedlgpcdasvads` 已经执行过，并跑通了验收脚本。**线上站点的数据库不在开发侧**，
所以这一步由店主侧（或上游 `KeMiaoDaDi` 的技术负责人）在他们的 Supabase 项目里执行一次，开发侧不需要也不应拿到线上库凭据。
顺序不能反，`017` 依赖 `016` 建的表和列。执行方式二选一：

- Supabase 控制台的 SQL Editor：粘贴全文，点 Run，看到 `Success. No rows returned` 即可。
- 或走 Management API：`docs/run_migrations.py`（需要 Personal Access Token，存到 `~/.hermes/secrets/supabase_pat`）。

两个文件都写得可以重复执行（`IF NOT EXISTS`、先 `DROP CONSTRAINT` 再加），手抖点两次不会坏。
旧版（v1.2）留下的 `member_benefits` 表、`member_vip_active` / `activate_member_vip` 函数也一并 `DROP ... IF EXISTS` 兜底清掉。

**3. 本地起服务**

```bash
npm install
npm run dev -- -p 3002
```

注意用 `http://localhost:3002` 访问，不要用 `127.0.0.1`。Next.js 16 把不同 host 视作跨源，会拦掉 dev 资源，页面看似正常但完全不 hydrate，所有点击都没反应。

**4. 验证**

```bash
node --test tests/member.test.ts   # 会员 28 项（全仓 72 项）
npx tsc --noEmit
npm run build
```

数据库层验收：`docs/verify_member_system.sql`，31 项检查，整个脚本在一个事务里跑，末尾 `ROLLBACK`，不会留测试数据。
走真实 HTTP 的验收：`docs/verify_via_api.py`（38 项）与 `docs/场景演练_via_api.py`（48 项）。

## 二、迁移做了什么

| 迁移 | 内容 |
| --- | --- |
| `016_members.sql` | 建 `members` 表（邮箱唯一身份、3 条约束、3 个索引、开 RLS）；给 `timer_sessions` 加 `member_id` 与 `reward_eligible` 两列（含 CHECK）；给 `bookings` 加 `idx_bookings_email_key` |
| `017_member_settlement.sql` | 建 `member_rewards`（4 个折扣类型 CHECK、4 个索引）；建 `member_visit_days` 视图；建 4 个函数：`ensure_member_rewards`、`settle_timer_session`（5 参数版换成 8 参数版）、`unsettle_timer_session`、`link_timer_session_to_member` |

`timer_sessions.reward_eligible` 是结算那一刻固化下来的判断（该单是否有会员归属），不是事后推算的：

- **true** = 会员本人正常结算的单，计入奖励进度；
- **false** = 后台把已结算的散客单补挂到会员名下，那一单只算到店次数、不计进度；
- **NULL** = 尚未判定（未结算的单、以及本迁移之前的历史订单）。

**迁移未执行前，应用照常工作**。这是刻意设计的：新代码在解析不出会员时不写 `member_id` 列；结算只在真的用会员折扣时才向 RPC 传新参数。所以计时、预约、优惠券、原有结算全都不受影响，只是会员功能不生效。

## 四、奖励制度（2026-10 改版）

到店次数按「自然日」算，同一天来多次只算一次。攒够次数解锁折扣奖励：

| 到店次数 | 奖励（一次性） | 实际折扣 | 举例（原价 £13.99） |
| --- | --- | --- | --- |
| 第 3 次 | **9 折** | 减 10% | £13.99 → £12.59 |
| 第 5 次 | **8 折** | 减 20% | £13.99 → £11.19 |
| 第 7 次 | **7 折** | 减 30% | £13.99 → £9.79 |
| 第 10 次 | **5 折** | 减 50% | £13.99 → £6.99 |

口径：

1. **一次性奖励**：每到一个节点解锁一张对应折扣，核销一次即用掉；不会重复发放、用完即止。
2. **每 10 次一轮**：第 13 / 15 / 17 / 20 次继续给 9 / 8 / 7 / 5 折，无限循环。解锁幂等靠 `UNIQUE(member_id, reward_type, cycle_index)`。
3. **折扣只能用在本会员本人的订单上**（`MEMBER_SESSION_MISMATCH` 对全部四档生效），不可转赠、没有朋友券。忘了以会员身份计时的，店员先用「挂订单」把单挂到会员名下再结算。
4. **刚解锁的奖励不能用于产生它的那笔消费**：折扣按结算前状态计算，奖励解锁放在结算成功之后，挑奖励时排除本单解锁的那张。
5. **折扣金额由 TypeScript 与 SQL 双算**：`lib/member/member.ts` 的 `computeMemberDiscount` 先算，`settle_timer_session` 用自己查到的奖励记录复核，对不上抛错。改动折扣逻辑必须两处一起改。
6. **后台禁操作**：后台不能手动加减到店次数、不能直接改进度、不能补发奖励、不能改邮箱、不能删历史。金额只在结算面板由服务端计算。

**两处替 PRD 补的解释，需要店主确认**：

1. **Link to Member 允许补挂已结算的订单**（业主 2026-09-16 确认）。PRD 5.2 没说时点。补挂只写归属、把 `reward_eligible` 记 false：到店次数 +1，折扣不退、奖励不补、已收金额不动；已经属于别的会员的订单不能改归属。未结算的单仍照旧挂，进度资格留空、等结算时判定。
2. **英文版暂不开放会员制度**（业主 2026-09-17 决定）。中文界面才有会员入口、计时表单的会员身份与预约页的加入勾选框；英文界面一律不出现，服务端在 `/api/bookings` 里另按 `lang === 'zh'` 拦一道。同一轮里中文界面的会员文案全部改成中文。

3. **`npm run lint` 跑不起来**，仓库根目录没有任何 eslint 配置。这是既有状态，未改动。

| 给什么 | 在哪 | 对方要做什么 |
| --- | --- | --- |
| **一页说明（直接转发给店主）** | `docs/给店主的一页说明.md` | 照着做：粘一次、按一次 Run，不到一分钟 |

| 验收脚本（可选） | `docs/verify_via_api.py` | 想复验就在有 service key 的机器上跑一次，应输出 38/38 |

**注意**：`docs/verify_via_api.py` 需要项目的 service key，只在对方自己的机器上跑。本仓库不含任何密钥。
